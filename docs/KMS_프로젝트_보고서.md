## 1. 프로젝트 개요

### 1.1 배경 및 목적

시스템기술1과가 보유한 핵심 기술 지식—공정별 노하우, 트러블슈팅 이력, 개선 사례 등—은 현재 개인 PC·공유폴더·구두 전달에 의존하고 있어 지식의 단절·손실 위험이 높고, 신규 팀원의 업무 습득에도 오랜 시간이 소요된다.

**시스템기술 KMS**는 이러한 부서 내 암묵지를 형식지로 전환하고, 누구나 신속하게 검색·활용할 수 있는 **웹 기반 지식 관리 포털**이다. 단순 문서 저장을 넘어 공정별 분류, 버전 이력, 태그 기반 연관 검색, 협업 알림, 업무 일정 관리까지 통합하여 부서 지식의 생산성을 높이는 것이 궁극적인 목표다.

### 1.2 시스템 명칭

| 항목 | 내용 |
|------|------|
| 시스템명 | 시스템기술 KMS (Knowledge Management System) |
| 서비스 형태 | 사내 웹 포털 (KKTY PORTAL 내 통합) |
| 대상 부서 | 시스템기술1과 (배합~성형 공정 담당 인원) |
| 개발 부서 | 정보시스템과 |
| 개발 예정 착수 | 2026년 10월 |

## 2. 주요 업무(기능) 구성 및 운용 방식

### 2.1 대시보드 및 통계

**역할:** 포털 진입 시 가장 먼저 보이는 홈 화면으로, 부서 지식 현황을 한눈에 파악할 수 있도록 한다.

| 구성 요소 | 내용 | 운용 방식 |
|-----------|------|-----------|
| 상단 요약 카드 | 전체 문서 수, 설비 등록 개수, 첨부파일 개수 | 데이터베이스 실시간 집계, 자동 표시 |
| 최근 등록 문서 | 최신 순으로 등록된 문서 목록 노출 | 등록 일시 기준 자동 정렬 |
| 공정별 문서 통계 | 연/월별 공정별 문서 수, 문서 유형별 분포(트러블슈팅·개선사례 등) | 필터 선택 시 차트·수치 동적 갱신 |

**운용 포인트:** 별도 관리 행위 없이 문서 등록·수정이 발생할 때마다 수치가 자동 반영된다. 관리자가 마스터 데이터(공정, 문서 유형)를 추가하면 통계 분류도 즉시 확장된다.

---

### 2.2 분류 및 마스터 관리

**역할:** 문서를 정확하게 분류하기 위한 기준 데이터(공정, 팀원, 문서 유형)를 관리한다.

#### 2.2.1 계·공정별 마스터 관리

- 배합, 성형 등 현재 운용 중인 공정 항목을 자유롭게 추가·삭제할 수 있다.
- 공정이 신설되거나 폐지되더라도 관리자가 직접 반영할 수 있어 유연성이 높다.

#### 2.2.2 팀원 관리

- 직책·사번 정보는 사내 HR 시스템 연동을 통해 자동으로 불러온다.
- 팀원이 소속된 '계' 정보는 HR 시스템에서 제공되지 않으므로 관리자가 수동으로 입력한다.

#### 2.2.3 문서 유형 마스터 관리

- 매뉴얼, 트러블슈팅, 개선사례 등 문서 유형 항목을 관리자가 직접 추가·삭제한다.
- 신규 유형 추가 즉시 문서 등록·검색·통계 항목에 자동 반영된다.

---

### 2.3 문서 작성 및 관리

**역할:** KMS의 핵심 기능. 기술 지식을 구조화된 양식으로 등록·검색·열람·수정한다.

#### 문서 등록 항목

| 입력 항목 | 설명 |
|-----------|------|
| 공정 | 배합, 성형 등 해당 공정 선택 |
| 설비 | 공정 내 대상 설비 선택 |
| 문서 유형 | 매뉴얼 / 트러블슈팅 / 개선사례 등 |
| 작성자 | 로그인 계정 자동 연동 |
| 제목 / 내용 | 지식 본문 작성 |
| 태그 | 검색 편의를 위한 키워드 등록 |
| 연관 문서 링크 | 관련 기존 문서 연결 |
| 파일 첨부 | 도면, 사진, 동영상 등 첨부 |
| 공유 폴더 경로 | 첨부파일이 자동 복사될 서버 경로 지정 (필수) |

#### 운용 포인트

- **태그·연관 문서**: 작성 시 유사 키워드를 태그로 달면 검색 결과에 풍부하게 노출된다. 연관 문서 링크를 통해 관련 지식끼리 네트워크를 형성한다.
- **버전 관리**: 문서 수정 시 이전 이력을 조회할 수 있어 변경 경위 추적이 가능하다 (희망 기능, 구현 우선순위 협의 필요).
- **출력 및 다운로드**: 문서 목록을 엑셀로 내려받거나 개별 문서를 인쇄할 수 있다.

---

### 2.4 파일 첨부 및 경로 관리

**역할:** 첨부파일을 지정된 공유 폴더에 자동 저장하고 경로를 문서에 연결하여 파일 소재를 명확히 한다.

| 항목 | 내용 |
|------|------|
| 저장 방식 | 문서 저장 시 서버 지정 경로로 첨부파일 자동 복사 |
| 경로 필수 여부 | 공유폴더 경로 미입력 시 문서 저장 불가 |
| 기본 경로 설정 | 관리자가 파일 저장 기본 경로를 사전 지정 가능 |
| 용량 제한 | 현재 서버 파일당 100MB 제한 (실제 필요 용량 추가 확인 필요) |

**운용 포인트:** 경로 지정을 강제함으로써 첨부파일이 개인 PC에 방치되는 것을 방지하고, 퇴직·이동 후에도 자산이 공유 서버에 보존된다.

---

### 2.5 협업 및 알림

**역할:** 문서 등록·변경 사항을 팀원에게 즉시 공유하고, 댓글을 통한 업무 피드백 환경을 제공한다.

| 기능 | 내용 |
|------|------|
| 메일 알림 | 문서 등록·저장 시 동일 계(係) 팀원에게 자동 메일 발송 |
| 댓글 기능 | 문서 내 댓글 작성으로 피드백 및 질의응답 가능 |
| 사내 메신저 | 보안 정책상 부서 전용 메신저 신설 불가 → 댓글 기능으로 대체 |

**운용 포인트:** 메일 알림 수신 범위는 '계' 단위로 설정되므로, 팀원 마스터에 계 정보가 정확히 입력되어 있어야 한다.

---

### 2.6 일정 및 업무 관리

**역할:** 부서 스케줄과 개인 업무 진행 상황을 한 화면에서 확인하고 관리한다.

| 기능 | 내용 |
|------|------|
| 부서 현황판 | 팀 스케줄표 및 업무 현황 한 눈에 조회 |
| 업무 관리 | 개인이 우선순위 설정, 진행 상태 클릭으로 완료 처리 |
| D-day 임박 표시 | 마감일 임박 업무 적색 강조 표시 |
| 주간 업무 메일 | 이번 주 업무 리스트 자동 메일 발송 |

## 3. 기존 포털과의 차이점

### 3.1 기술 스택 비교

| 구분 | 기존 포털 | 시스템기술 KMS (신규) |
|------|-----------|----------------------|
| 프론트엔드 언어 | PHP (서버 사이드 렌더링) | **React + TypeScript** (컴포넌트 기반 SPA/SSR) |
| UI 프레임워크 | 자체 PHP 템플릿 | **Next.js + Tailwind CSS** |
| 상태 관리 | 페이지 리로드 방식 | **Zustand** (클라이언트 전역 상태 관리) |
| 렌더링 방식 | 전체 페이지 새로고침 | 부분 렌더링(컴포넌트 단위 업데이트) |
| 타입 안전성 | 없음 | **TypeScript**로 타입 오류 컴파일 단계에서 차단 |

### 3.2 사용자 경험(UX) 차이

| 구분 | 기존 포털 (PHP) | 신규 KMS (React) |
|------|----------------|-----------------|
| 화면 전환 속도 | 매 요청마다 전체 페이지 로드 | 변경된 컴포넌트만 갱신, 전환 즉각적 |
| 검색·필터 반응 | 필터 적용마다 페이지 리로드 | 입력 즉시 결과 반영 (실시간 UI) |
| 인터랙션 | 폼 제출 후 결과 페이지 이동 | 모달·탭·드래그 등 풍부한 상호작용 |
| 유지보수 | 기능 추가 시 HTML·PHP 로직 혼재 | UI 컴포넌트 단위 재사용·교체 용이 |

### 3.3 개발·운영 측면 차이

| 구분 | 기존 포털 (PHP) | 신규 KMS (React) |
|------|----------------|-----------------|
| 코드 재사용 | 복붙 방식의 HTML 반복 | 컴포넌트 단위 재사용, 코드 중복 최소화 |
| 테스트 가능성 | 통합 테스트 위주 | 단위(unit) 테스트·스냅샷 테스트 가능 |
| 확장성 | 기능 추가 시 파일 비대화 | 기능별 모듈 분리로 확장 용이 |
| 팀 협업 | 파일 단위 충돌 빈번 | 컴포넌트 단위 분업, Git 충돌 최소화 |
| 빌드·배포 | 파일 직접 업로드 | CI/CD 파이프라인 구성 가능 |

## 4. React 도입에 따른 개발 기간 증가 이유 및 기대 효과

### 4.1 초기 투자 비용이 증가하는 이유

React 기반 개발은 PHP 방식 대비 초기 환경 구성과 설계에 더 많은 시간이 필요하다.

| 원인 | 설명 |
|------|------|
| 개발 환경 구성 | Node.js, Next.js, TypeScript 빌드 파이프라인 설정 필요 |
| 컴포넌트 설계 | 재사용성을 고려한 UI 컴포넌트 구조 사전 설계 |
| 상태 관리 설계 | 전역·로컬 상태 분리 및 데이터 흐름 정의 |
| API 설계 분리 | 프론트엔드·백엔드 역할 명확히 분리 (REST API 설계 별도 필요) |
| 팀 학습 곡선 | PHP 대비 React·TypeScript 숙련도 확보 시간 |

이러한 이유로 **기존 시스템 UI 활용 시 3~5개월**, 신규 UI·언어 변경 시 그 이상의 기간이 소요될 것으로 예상된다.

### 4.2 React 도입 후 기대 효과

| 기대 효과 | 구체적 내용 |
|-----------|------------|
| **빠른 사용자 경험** | 페이지 이동 없이 즉각적 화면 갱신으로 업무 효율 향상 |
| **높은 유지보수성** | 기능·화면 단위 컴포넌트 분리로 특정 기능만 수정·교체 용이 |
| **재사용성** | 공통 버튼, 모달, 테이블 등 UI 컴포넌트를 사내 다른 시스템에도 재활용 가능 |
| **타입 안전성** | TypeScript로 런타임 오류를 컴파일 시점에 사전 차단 |
| **확장 용이성** | 신규 기능(모바일 대응, 알림 센터, 대시보드 위젯 추가 등) 독립적 모듈로 확장 |
| **기술 자산 축적** | React 개발 노하우가 이후 사내 포털 전반의 현대화 기반으로 활용 가능 |
| **미래 표준 대응** | 국내외 엔터프라이즈 프론트엔드 표준이 React/Vue 등 컴포넌트 기반으로 이동 중 |

**결론:** 초기 개발 기간은 기존 PHP 방식 대비 길어지나, 완성 후의 유지보수 비용·기능 추가 속도·사용자 만족도에서 장기적으로 우위를 점한다. 이번 KMS가 KKTY PORTAL의 React 전환 첫 사례가 되어 이후 시스템 현대화의 기반이 될 것으로 기대된다.
